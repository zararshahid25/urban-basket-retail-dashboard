# Urban Basket — run and rebuild manual

This training project uses PostgreSQL/pgAdmin, Excel, Power Query and Power BI. No Python or Streamlit installation is needed. The supplied source fixtures are simulated Pakistani retail orders dated January 2024–December 2025. The portfolio project is dated 2026.

## 1. What you will learn

Build constrained relational tables; load raw CSVs into staging; resolve duplicates and inconsistent cities; quarantine scenario exceptions; apply exact decimal arithmetic; aggregate at the correct grain; build an Excel reporting workbook; connect a Power BI star model; write DAX measures; reconcile filters and totals.

Allow several practice sessions. Work through SQL, then Excel, then Power BI. Keep a separate practice copy so you can compare your result with this package.

## 2. Requirements and files

- Windows computer for Power BI Desktop. Use a current Desktop release with Power BI project/PBIR support.
- PostgreSQL 16 and pgAdmin 4. The PostgreSQL installer includes psql, the command-line SQL client.
- Excel desktop with Power Query. The delivered workbook opens without a database connection.
- Extract the whole project to a simple path such as `C:\Projects\urban-basket-retail-dashboard`. Keep all Power BI folders together.

## 3. Create the database in pgAdmin

1. Connect to your local PostgreSQL server. Use your own password.
2. Right-click Databases → Create → Database. Name it `urban_basket`.
3. Open Query Tool on that database. Check `SELECT current_database();` returns `urban_basket`.
4. Use the dedicated project database only. The repeatable load replaces its `retail` project tables. Do not run it against a database containing work you want to preserve.

### Recommended repeatable load with psql

Open PowerShell in the extracted project folder. Run:

```powershell
psql -h localhost -p 5432 -U postgres -d urban_basket -f sql/run_all.psql
```

Enter your password when prompted. If `psql` is not on PATH, use its actual installed path, for example:

```powershell
& "C:\Program Files\PostgreSQL\16\bin\psql.exe" -h localhost -U postgres -d urban_basket -f sql/run_all.psql
```

Run from the project root: CSV paths and `\i` includes are relative to that working directory. `ON_ERROR_STOP` stops on the first error. The runner creates staging and constrained tables, imports five sources, transforms them, creates views and checks every enriched row against the reference fixture. Run it a second time to confirm repeatability.

In pgAdmin, refresh Schemas → retail → Tables/Views. Query:

```sql
SELECT * FROM retail.kpi_summary;
SELECT issue, count(*) FROM retail.data_issues GROUP BY issue ORDER BY issue;
```

### GUI import alternative for learning

Start in a new, empty `urban_basket` database. Execute `00_staging.sql`, then `01_schema.sql` using Query Tool. Import these CSVs using each table's Import/Export Data dialog, CSV format, UTF-8, header enabled, delimiter comma and quote double-quote:

Use the recommended runner for the full automated reconciliation. A fresh GUI import does not itself prove the reference comparisons passed.

## 4. Understand and reproduce preparation

The relational source model has categories → products → order_items ← orders ← customers. The report view has one row per accepted order item. Join to products once by product_id, orders once by order_id and customers once by customer_id. Never join line-level data to an unaggregated second line table.

1. Retain the first raw occurrence of each order_id using `ROW_NUMBER() OVER(PARTITION BY order_id ORDER BY source_row)`. Four later rows are excluded. A different source may require a different, documented survivorship rule.
2. Match `lower(trim(city))` against a canonical mapping. Unknown cities raise an assertion instead of silently disappearing in a join. There are 48 customer-city changes and 287 shipping-city changes, the latter counted on raw rows including duplicates.
3. Retain quantity 1–20. Six item rows are quarantined in the raw source and logged. This range is a declared training assumption; larger real orders are not automatically invalid.
4. Recompute each accepted revenue line with SQL `NUMERIC`:

```sql
round(quantity * unit_price * (1 - discount_pct / 100), 2)
```

5. Recompute each cost line as `round(quantity * products.unit_cost, 2)`. The static product reference cost is a scenario simplification; it is not historical inventory accounting.
6. Apply a status multiplier: Completed = +1, Returned = −1, Cancelled = 0. Multiply revenue, revenue minus cost, and quantity by that sign.
7. Confirm every order has at least one accepted item and the enriched view has exactly as many rows as accepted items. An order with no valid items must trigger a decision before publishing.

The source has 326 accepted revenue rows that differ from exact recomputation. The policy rounds each line half away from zero to two decimals. Adding rounded lines and rounding the grand total are different operations.

Staging uses typed dates/numbers for this known fixture. Unexpected malformed text fails the load. It is not a general-purpose parser for arbitrary corrupt CSVs. No tax, delivery charge, original-sale linkage or return-event date is available.

## 6. Use and rebuild the Excel workbook

Open `Urban_Basket_Retail.xlsx`. Dashboard B4 is the yellow channel selector. Choose Web and observe that all four KPIs and three charts change. Restore All. The other tabs expose monthly formulas, category formulas, prepared lines, unique orders, quality controls and definitions.

The supplied workbook holds a prepared snapshot. It does **not** contain an embedded live Power Query connection. SQL owns cleaning/line arithmetic; Excel owns the aggregation formulas. Raw CSVs remain separate to avoid duplicating source and cleaned records inside the workbook.

### Build your own import

1. Create a blank workbook. Data → Get Data → From Text/CSV → select `data/reference/sales_enriched.csv` → Transform Data.
2. Name it SalesLines. Use Date for order_date/order_month; Whole Number for quantity, IDs and net_units; Decimal Number or Fixed Decimal Number for monetary columns; Text for order/customer IDs and categories. Parse ISO source dates, then display dates as `dd/mm/yyyy` in Excel.
3. Close & Load to a table on Sales Lines. Repeat for `orders.csv` on Orders, named OrdersData. That table must have one row per order.
4. Alternatively import `retail.sales_enriched` and `retail.orders` through Excel's PostgreSQL connector if available in your Excel environment. Keep the same columns and types. The CSV route is sufficient for this exercise.
5. Recreate Dashboard, Monthly Trends and Category Review using the delivered workbook as the comparison copy. Use Data Validation → List in B4: `All,Web,Mobile App,Marketplace`.
6. Monthly Trends uses 24 month-start dates. Category Review uses the eight category names from the fixture. Use `SUMIFS`, `COUNTIFS`, `EDATE` and explicit zero-denominator handling.

For a channel-aware net-sales formula using table references:

```excel
=SUMIFS(SalesLines[net_revenue],SalesLines[sales_channel],IF(Dashboard!$B$4="All","*",Dashboard!$B$4))
```

Completed order count uses **OrdersData**, not SalesLines:

```excel
=COUNTIFS(OrdersData[order_status],"Completed",OrdersData[sales_channel],IF(Dashboard!$B$4="All","*",Dashboard!$B$4))
```

For monthly sales, add the month criterion against SalesLines[order_month]. For monthly completed orders, filter OrdersData[order_date] `>=` month start and `<` EDATE(month start,1). Completed AOV divides completed line revenue by completed unique orders under the same channel/month filters. Return rate divides returned orders by completed plus returned orders. Do not count sales lines as orders.

The supplied workbook uses bounded cell ranges for this fixture. If adding rows, extend every source range and month list; inserting into an Excel Table alone does not extend those existing formulas. In your rebuild, structured references make extending rows easier. If adding category filters, calculate a distinct category-order bridge or use the Excel Data Model; the unique Orders table has no category field.

Recreate the charts: monthly net sales as a line, category net sales as bars, category gross profit as bars. Bind charts to formula summary cells. Format currency with PKR labels, margin/rates as percentages and dates as month/year. Use the workbook's green and amber colors consistently. Never average the per-row margins.

## 8. Rebuild Power BI from a blank file

1. Get Data → PostgreSQL database → server/database above → Import → Transform Data.
2. Load `retail.sales_enriched` as FactSales, `retail.dim_products` as DimProducts, `retail.customers` as DimCustomers and `retail.dim_date` as DimDate. The M in `powerbi/queries/` documents the exact navigation. Create Server and Database text parameters if pasting those queries in Advanced Editor.
3. In Model view create single-direction one-to-many relationships:
   - DimProducts[product_id] → FactSales[product_id]
   - DimCustomers[customer_id] → FactSales[customer_id]
   - DimDate[date] → FactSales[order_date]
4. Sort DimDate[year_month] by DimDate[month]. Use DimDate for date slicing. Mark DimDate[date] as the date table in your manual rebuild. Disable automatic date/time for this file if it adds unwanted hidden date tables.
5. Use Fixed Decimal Number for currency. Hide duplicate descriptive FactSales fields category_name/product_name/customer_segment. Build product/category slicers from DimProducts and segment visuals from DimCustomers.
6. Create each measure in `MEASURES.dax` separately. Put them on FactSales. Set currency formats to two decimals, counts to whole numbers, rates to one or two percentage decimals.
7. Create three 1280 × 800 pages. Use `visual_inventory.json` for exact chart types, fields and positions. Every page has month/channel/category slicers. Overview has four KPI cards and four charts. Product review has a category scorecard, category profit chart and product table. Channel review has three order-status cards, a channel scorecard and city/segment charts.
8. Import the provided theme. Maintain clear chart titles and PKR labels. Use normal bar/line charts and tables; additional custom visuals are unnecessary.

MoM/YoY measures deliberately return blank when more than one month is in context. They are intended for monthly chart points or a single selected month. The first month has no prior-month comparison; all of 2024 has no previous-year comparison in this fixture. Category Sales Share is the share among selected categories, with the other current filters retained.

### Desktop acceptance checklist

- All four overview KPIs match section 5 when filters are clear.
- Web selection gives the same net sales and AOV in Excel and Power BI.
- A category selection counts distinct orders. Summing displayed category order counts must not be used as the all-category total.
- Multi-select months and categories. Check totals recompute rather than averaging visible row rates.
- Select January 2024: prior-month and prior-year measures are blank. Select January 2025: YoY uses January 2024.
- Return rate always uses completed + returned order counts; cancelled orders are excluded.
- Refresh twice; counts and KPIs remain stable. Check every page for clipped labels, blank unexpected visuals, incorrect sorting and slicer interactions.
- Save screenshots **from Desktop** only after these checks. The repository's Excel preview is explicitly labelled as Excel, not as a Power BI screenshot.

## 9. SQL exercises and learning checks

Run each question in `04_questions.sql` separately. Explain its grain before running it. It includes category contribution, a DENSE_RANK top-products query, a distinct-order category return rate, correlated subqueries and LAG month-over-month comparisons.

Practice questions:

1. Why is COUNT(*) from sales_enriched larger than the number of orders? Explain the one-to-many relationship.
2. Why is net sales / completed orders not the defined completed AOV? Returns have changed the numerator only.
3. Why can category order counts sum above 9,000? One order can span multiple categories.
4. Why does AVG(gross_profit/net_revenue) not give the overall margin? It weights each line equally rather than by sales.
5. Why are the first MoM value and 2024 YoY values blank? Their comparison periods are unavailable.
6. Inspect the six quarantined item rows. Propose a different quantity policy for bulk orders, explain its consequences and compare counts before changing it.
7. Add an index on orders(order_date) in your practice database, run EXPLAIN ANALYZE on a date-filtered query, and explain why a small dataset may still use a sequential scan. Do not claim a speedup without measured evidence.

## 10. Refresh, troubleshoot and publish honestly

For unchanged fixtures, rerun `run_all.psql`, then refresh Power BI. To export clean SQL results, run `psql ... -f sql/export_reference.psql` from the project root. This overwrites the reference CSVs. Do not export immediately before validation to make a discrepancy disappear: investigate differences against the committed baseline first. If using genuinely changed data, version it separately, revise the dated reference controls and document why expected counts changed.

Common problems: connection refused → start PostgreSQL/check port; password failure → correct Data source permissions; missing retail views → run the loader in the right database; missing CSV → correct working directory; source_row import failure → omit the identity column in GUI; date mismatch → use actual Date types; AOV too low → inspect numerator/status filters; inflated counts → use distinct order IDs.

Present this as a **simulated training project**. Claim the work you understand and have reproduced. Do not imply employer/client work, production deployment, measured business impact, accounting certification or real customer records. Review `PORTFOLIO_NOTES.md` after completing the Desktop checklist. Native Desktop execution is the remaining environment-specific verification, not something established by a JSON schema pass.
